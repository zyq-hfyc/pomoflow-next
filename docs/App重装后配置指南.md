# App 重装后配置指南(服务器地址 + 登录 + 数据恢复)

> **场景**:移动端卸载重装 / 换机 / 新装后,登录页要填服务器地址 —— 填错
> 就是「点登录无任何反应」(请求默默超时,无报错弹窗)。本文永久记录正确
> 地址、网络链路、重装步骤与排查,避免每次重装都重新踩一遍。
>
> 建立于 2026-09-04(release 0.2.0 装机实测登录成功)。

## 一句话结论:该填哪个地址

| 端 | 填的地址 | 为什么 |
| ---- | ---------- | -------- |
| **手机 App**(Wi-Fi) | `http://192.168.3.29:8080` | 走 Windows 宿主机的端口转发进来 |
| **桌面端 App**(装在 VM 宿主机上) | `http://192.168.75.128:8080` | 与 VM 同机,直连 NAT 网段没问题 |
| **浏览器 · 移动端 Web**(宿主机 Chrome) | 登录页填 `http://192.168.75.128:8080` | 宿主机浏览器直连 VM;服务端 CORS 已放行 Web 跨域 |
| **浏览器 · 桌面端 UI**(宿主机) | `http://localhost:1420` | Vite 开发服务器;**仅界面预览**,数据功能不可用(见下) |

> ⚠️ **手机上填 `192.168.75.x` 一定「无反应」** —— 那是 VMware 的 NAT
> 内网段,只有宿主机自己路由得到;手机在 Wi-Fi 上发的包根本到不了。
> 2026-09-04 踩过:症状即「点登录无任何反应」,没有任何报错。

## 网络链路

```
手机 ──(同一 Wi-Fi 局域网)──▶ Windows 宿主机 192.168.3.29:8080
        ──(netsh portproxy 端口转发)──▶ VM 192.168.75.128:8080(sync-server)
```

桌面端 App 与 VM 同在宿主机上,直接填 `http://192.168.75.128:8080`,
不经过转发。

## 浏览器访问(开发预览)

### 移动端 Web(Flutter Web)

```bash
export PATH="/d/SoftWareInstall/flutter_3.47.1/bin:$PATH"
cd apps/mobile
flutter run -d chrome                    # 开发预览,自动开 Chrome(随机端口)
# 或固定端口: flutter run -d chrome --web-port=8090
```

- **登录页服务器地址**:`http://192.168.75.128:8080` —— 宿主机上的浏览器
  直连 VM 即可,不用绕转发(填 `192.168.3.29:8080` 也通,但多一跳)
- 跨域没问题:服务端 CORS `allow_origin(Any)` 专为 Flutter Web 预览放行
  (`services/sync-server/src/main.rs` 的 CorsLayer)
- 正式产物 `flutter build web --release` 出在 `build/web/`,是静态文件,
  需要时自行起静态服务器(如 `python -m http.server -d build/web 8090`)

### 桌面端 UI(Svelte,Vite dev)

```bash
npm --prefix apps/desktop/ui run dev      # → http://localhost:1420
```

- 端口固定 **1420**(Tauri 约定,`ui/vite.config.ts`,改了 Tauri 就找不到)
- ⚠️ **只能看界面壳**:UI 的数据层全是 Tauri `invoke`(Rust 命令,
  `ui/src/lib/api.ts`),纯浏览器里没有 Tauri 运行时,**所有数据操作
  不可用** —— 它是 Tauri 窗口内嵌页面的开发预览口,不是「Web 版桌面端」
- 桌面端不需要填服务器地址(同步后端在本机 Rust 进程内,不走浏览器 HTTP)

## 端口转发规则(宿主机上执行,需管理员)

**查看**(这条规则 2026-09-04 确认仍在,portproxy 持久、重启不丢):

```
netsh interface portproxy show all
```

预期包含一行:

```
192.168.3.29    8080    192.168.75.128    8080
```

**探活**(宿主机上跑,验证转发链路通):

```
curl http://192.168.3.29:8080/healthz
```

预期:`{"ok":true,"service":"sync-server"}`

**重建**(仅当规则丢失 / 宿主机 IP 变化时):

```
netsh interface portproxy add v4tov4 listenaddress=192.168.3.29 listenport=8080 connectaddress=192.168.75.128 connectport=8080
```

> 注意:规则**绑定的是具体 IP** `192.168.3.29`(宿主机 Wi-Fi IP)。
> DHCP 换网 / 换路由器后此 IP 变了 → 先删旧建新:
> `netsh interface portproxy delete v4tov4 listenaddress=<旧IP> listenport=8080`
> 再用新 IP add,且手机端要改填新 IP。

## 连不上时的依赖排查(按序)

1. **VM 开机且 sync-server 在跑**:宿主机 `curl http://192.168.75.128:8080/healthz`
2. **手机与宿主机同一 Wi-Fi**:不同网段自然不通
3. **宿主机 IP 仍是 192.168.3.29**:`ipconfig` 核对(变了就重建转发,见上)
4. **Windows 防火墙放行 8080 入站**:2026-09-04 实测已通,正常情况不动;
   若手机连不上而宿主机自 curl 通,查入站规则

| 症状 | 最可能原因 | 处理 |
|------|-----------|------|
| 点登录无任何反应 | 手机填了 `192.168.75.x`,或宿主机 IP 变了 | 改填 `192.168.3.29:8080`;ipconfig 核对 |
| 登录报网络错误 | VM 没开 / 服务没跑 | 宿主机 curl healthz 定位 |
| 宿主机 curl 通、手机不通 | 防火墙 8080 入站 / 不在同一 Wi-Fi | 查入站规则与 Wi-Fi |
