## 议题一:现有项目打包成跨平台可执行程序的原理

**问题**:当前项目能打包成 .exe / mac / linux 通用软件的原理是什么?依赖什么工具?

**核心结论**:

- **依赖工具**:PyInstaller(核心)+ UPX(压缩)+ GitHub Actions matrix(跨平台)。
- **本质**:PomoFlow 不是传统 GUI 桌面应用,而是「本地 FastAPI 服务 + 前端静态资源 + SQLite 数据库」塞进一个单文件可执行程序,双击后在 `localhost:8709` 起服务并自动开浏览器。
- **PyInstaller 原理**:静态分析 import 链 → 收集 CPython 解释器 + 字节码 + C 扩展 + 数据文件 → 打成自解压归档(前面拼 C bootloader)→ 运行时解压到临时目录 `sys._MEIPASS` 启动。
- **跨平台关键**:PyInstaller 不能交叉编译,靠 CI 在 Windows/macOS/Linux 三个 runner 上**各自**打包,产出各平台二进制。
- **项目特殊设计**:`hiddenimports` 显式声明路由(FastAPI 动态 import);前端 `npm run build` 后 cp 到 `app/static` 打入包;`run.py` 用 `sys.frozen` + `os.chdir` 锚定 exe 目录,把用户 SQLite 持久化到 exe 旁(区别于临时目录里的只读资源)。

## 议题二:Electron / Tauri / PyQt 的区别与联系

**问题**:三者的区别和联系?

**核心结论**:三者分属**两个流派**。

| 维度 | Electron | Tauri | PyQt |
|------|----------|-------|------|
| UI 渲染 | 内嵌完整 Chromium | 系统 WebView(Win=WebView2/Mac=WKWebView/Linux=webkitgtk) | Qt 原生控件 / QML |
| 后端语言 | Node.js(TS/JS) | Rust | Python |
| 体积/内存 | 大 | 小 | 中 |
| 跨平台一致性 | 极高(同款 Chromium) | 较高(各平台 WebView 有细微差异) | 高(Qt 统一渲染) |
| 典型应用 | VS Code、Discord、Slack | 轻量工具(新星) | 科学计算 GUI、传统桌面 |

- **联系**:都是跨平台桌面 GUI 框架,需打包分发,都有前后端分层,都能调系统原生能力。
- **关键判断**:对一个已有 React 前端的项目,迁 Tauri/Electron 的成本远低于 PyQt(后者要重写 UI)。

## 议题三:Node.js / Rust / Python 桌面后端优劣 + 移动端/云端规划下的推荐

**问题**:三语言在桌面后端的优劣?目前/未来流行度?若有移动端 + 云端 + 微服务规划,推荐哪种?

**核心结论**:

- **优劣**:Node 省心生态全但笨重;Rust 性能/安全最强但上手陡;Python 开发快但性能弱、移动端死路。
- **流行度分层**:Electron 是现在王者,Tauri 是上升新星,PyQt 桌面在收窄;Rust 是未来系统级方向。
- **关键洞察**:该规划已**超出桌面 GUI 选型范畴**——移动端的真正标准答案是 React Native / Flutter,不在三者中。
- **初步推荐(分层解耦)**:保留并强化 Python/FastAPI 后端(天然适合云端微服务),桌面 Tauri/Electron,移动 RN/Flutter。**核心忠告:不要为 GUI 选型而重写本可复用的后端。**

## 议题四:从零设计整体架构(初版方案)

**问题**:抛开现有架构,从零设计。需求:桌面(Win/Mac/Linux)+ 移动(iOS/安卓/鸿蒙);每端本地 SQLite 离线全功能;登录后按需同步到云端;云端弹性可扩展微服务;独立内网管理后台。

**初版方案**:

| 层 | 技术 |
|----|------|
| 移动端 | Flutter + Drift(Dart) |
| 桌面端 | Tauri 2 + React + TypeScript |
| 云端微服务 | Go(gin/echo) |
| 云端库 | PostgreSQL + Redis + NATS |
| 同步 | Change-Log + LWW + UUID |
| 管理后台 | React + Ant Design Pro |
| 部署 | Docker + Kubernetes |

## 议题五:三个选型追问(澄清选型逻辑)

> 这一轮是关键——把"为什么这么选"的逻辑彻底摊开。

**追问 1:移动端为什么不选 uni-app?**
- uni-app 的杀手锏是**微信小程序**,本项目无小程序需求;且 **Flutter 鸿蒙为华为官方主线支持,成熟度 > uni-app 的适配**。
- 反转:若需求包含微信小程序,uni-app 会反过来胜出。**选择由平台清单驱动,不是通用强弱。**

**追问 2:桌面端为什么从 Tauri+Rust 改成 Tauri+TS?**
- **诚实结论**:这不是"现方案更优",而是**约束变了**——初版为满足"桌面端前后端语言统一"约束,被迫让 Rust 退化为薄壳。这放弃了上一轮主推的 Rust 性能/安全卖点。
- **修正**:better-sqlite3 是 Node 模块,**不能配 Tauri**(Tauri 无 Node 运行时);Tauri+TS 访问 SQLite 应走 `tauri-plugin-sql`(底层 rusqlite)。

**追问 3:云端微服务为什么 Go,不选 Java/Python?**
- Go 的甜区:**启动快 + 镜像小 + goroutine 轻并发 = 云原生弹性扩缩**,K8s 母语。
- 诚实承认:Java 生态最全(适合复杂业务),Python 数据/AI 霸主(适合统计)。**微服务本就应多语言按领域选,不必全栈一种。**

## 议题六:约束更新与方案升级(关键转折)

**新约束**:
1. 桌面端不要"前后端语言统一",而要"Mac/Win/Linux 都能跑 + **性能安全优先** + 三端体验一致" → 应回到 **Tauri + Rust(业务逻辑写 Rust)**。
2. **不考虑招人**(人定方向、AI 编码实施),云端按"语言擅长领域"选最优、最精细的方案。

**升级后的最终方案**:

| 层 | 技术 | 语言 |
|----|------|------|
| 移动端 | Flutter + Drift | Dart |
| **桌面端** | **Tauri 2 + Rust 业务层 + Web UI** + rusqlite 直连 | **Rust** |
| **云端 Sync / Auth** | axum + tokio + sqlx | **Rust** |
| 云端 User / Membership / Notification | gin / echo | Go |
| **云端 Analytics** | FastAPI + pandas / Polars | **Python** |
| 网关 | APISIX | — |

**最大架构红利——Rust `core` crate 跨端复用**:桌面端与云端 Sync 都是 Rust,核心域逻辑(域模型 / 同步协议 / LWW 合并 / 校验)抽成 `pomoflow-rs` workspace 的 `core` crate,两端共享同一份代码。**合并算法两端零漂移**——这是 TS/Go/Python 方案结构上做不到的(只有 Rust 同时存在于桌面与云端)。

## 最终架构定稿

→ 沉淀为 [`architecture.md`](./architecture.md):14 节正文 + **ADR-001~008** 架构决策记录 + P0 产出物与验收标准。

**8 条关键决策(ADR 浓缩)**:

| ADR | 决策 | 核心理由 |
|-----|------|----------|
| 001 | 桌面与移动独立技术栈,不强行统一 | 各端用该平台最优技术 |
| 002 | 移动选 Flutter | 鸿蒙官方支持;排除 uni-app(无小程序)/ RN(鸿蒙弱) |
| 003 | 桌面选 Tauri+Rust(业务写 Rust) | 性能/安全/跨端一致 |
| 004 | 云端多语言微服务,按领域选型 | AI 编码释放多语言红利 |
| 005 | Rust `core` crate 桌面+云端共享 | 合并算法零漂移 |
| 006 | 同步用 LWW,不用 CRDT | 任务管理类够用、可控 |
| 007 | JWT + `user_id` 数据隔离 | 多端会话 + 最小权限 |
| 008 | 管理后台经 Admin BFF,不直连库 | 安全 + 审计 |

## 讨论中沉淀的方法论

1. **约束驱动选型**:技术选型没有银弹,关键约束变,答案就要调整。先摊开约束,再选型。
2. **关键逻辑单点定义**:易错的跨端逻辑(如同步合并)应共享同一份代码,而非两端重写。
3. **微服务多语言是优势不是负担**:每个服务用它领域最强的语言——前提是有 AI 编码移除人力成本约束。
4. **Local-first**:网络是可选增强,本地 SQLite 是真相源之一,离线必须完全可用。
5. **架构基线 + ADR**:把"是什么"和"为什么"都写进文档,未来争议有据可依。
